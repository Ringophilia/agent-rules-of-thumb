# 先查，再磕

AI 排错和写代码时有个很贵的习惯：**明明是别人早就解决过的问题，却从零开始自己推。**

- **排错**：看到第三方库或工具的报错，先自己猜原因，改一处、跑一次、再改一处……五六轮之后才去搜，或者一直不搜。其实把报错原文一搜，第一页就是官方 issue 和修法。
- **写代码**：CSV 解析手写 `split(',')`，日期加减自己算，重试和超时自己拼，然后边界情况一个个踩：引号里的逗号、字段里的换行、时区、夏令时、闰年。标准库或成熟的包早就把这些都处理好了。
- **凭记忆用 API**：参数名、默认值、配置项按印象写，报错了再猜另一个写法。训练数据有截止日期，库会改名、弃用、换默认值；当前版本的文档才是准的。

算一笔账：一次搜索 30 秒到 2 分钟。一轮"猜、改、跑"要几分钟，猜错了方向还会越走越深，顺手留下一堆为了"试试看"而改动的代码。**第一页搜索结果能省掉的，常常是一个小时。**

## 什么时候先查

### 排错时

出现下面任意一条，**先搜，再动手改**：

- 报错来自**不是你写的代码**：第三方库、框架、编译器 / 链接器、包管理器、构建工具、操作系统、驱动、数据库、云服务或 API 返回的错误。第一次见到就搜，最迟在**第二次修改之前**。
- **两次规则**：同一个问题，两种思路不同的修法都失败了。停下来，不要试第三种，先查。
- 你发现自己在**"试试看"**：改参数、换版本、加 flag、删缓存重装，却说不出为什么这样改应该有用。
- 现象很怪、**和文档说的不一样**：很可能是已知 bug、版本不兼容或平台差异。
- 看不懂的**错误码**：退出码、HRESULT、errno、HTTP 状态码加上服务自己的错误码。

### 写代码时

- 要实现的是**通用问题**：解析（CSV、JSON 流、日期时间、URL、命令行参数、ini/toml/yaml）、编码转换、时区、重试 / 退避 / 限流、鉴权和签名、加密和哈希、diff、模板、并发控制、缓存、文件格式（PDF、Excel、图片、压缩包）、协议客户端（HTTP、WebSocket、SMTP、串口）。
- 要用一个**不熟的、或者可能变过的** API、库、CLI。先看当前版本的文档、示例或类型定义，不要凭印象写。
- 要接入某个**外部系统**：它通常有官方 SDK、官方示例，或者有人踩过的坑。
- 心里冒出"**这个肯定有人做过**"的念头。

### 先查自己的仓库

"查"也包括项目本身，而且往往最准：

- 项目里**已经有的依赖**能不能做（`package.json`、`requirements.txt`、`*.csproj`、`go.mod`）？
- 有没有**现成的工具函数**？用 `rg` 搜一下函数名、关键字。
- `git log -S '<关键字>'` / `git log --grep`：以前有没有人修过同一类问题？

### 不用查的情况

- 报错指向你自己刚写的那一行，原因一眼就能看出来：拼写、语法、类型、漏了 import、变量名写错。
- 纯属你自己代码里的业务逻辑错误。
- 你很确定、而且最近刚验证过的事。

## 怎么查

### 排错：用报错原文搜

1. **复制原文，不要自己概括。** 你概括出来的描述，和别人遇到同一问题时写下的标题对不上。
2. **去掉本机特有的部分**：路径、用户名、主机名、PID、内存地址、时间戳、随机 ID、行号。**保留**错误码、异常类名、关键短语。
3. **加上上下文**：库名、版本号、平台（`<错误原文> <库名> <版本>`）。
4. 第一轮没结果：缩短（只留错误码或异常名加库名），或换一种说法，或换语言。

中文 Windows、中文本地化的工具给出的是中文报错，搜英文原文或错误码往往结果多得多（错误码在所有语言里都一样）；国内生态的库和服务，用中文搜。

### 去哪查（按可信度）

| 来源 | 适合 | 注意 |
| --- | --- | --- |
| 官方文档、迁移指南、changelog / release notes | API 用法、"升级后坏了" | 看清对应的版本 |
| 官方 issue tracker（**含已关闭的**） | 已知 bug、workaround、哪个版本修好的 | 读到 maintainer 的结论，不要只看楼主 |
| 源码、类型定义、本机已装的包 | 文档没写清楚的行为 | `node_modules/`、`site-packages/` 里就有，离线也能看 |
| 代码托管上的代码搜索 | 别人实际是怎么调用的 | 挑维护中的项目 |
| Stack Overflow、论坛 | 常见坑 | 看回答日期和票数，和你的版本对一对 |
| 博客、教程 | 整体思路 | 常常过时，尽量找原始出处 |

本机也有不少现成的"文档"：`<tool> --help`、`man`、`Get-Help`、`python -m pydoc`、`certutil -error <code>`（Windows 错误码）、`net helpmsg <n>`。

### 写代码：找成熟方案

1. **标准库优先**：Python `csv`、`datetime` / `zoneinfo`、`urllib.parse`、`argparse`、`difflib`；.NET 的 `System.Text.Json`、`TimeZoneInfo`；Node 的 `URL`、`util.parseArgs`……
2. **项目已有依赖其次**：已经装了的就别再引入一个同类的。
3. **再看成熟的第三方包**：最近有发布、用的人多、issue 有人回、许可证兼容、依赖不重。
4. **官方 quickstart / 示例**比博客可靠：它和当前版本一起维护。

**引入新依赖是项目决策。** 项目明确要求零依赖或依赖很少时（例如本仓库的脚本只用系统自带的 PowerShell 和 .NET），不要直接加：用标准库做；或者把"用某个包能省掉哪些边界情况"讲清楚，问用户。

## 查到之后

- **对版本、对平台**：答案针对哪个版本、哪个系统？你的是哪个？很多"不管用"其实是版本不对。
- **弄懂为什么能修，再用**：不要原样照抄。尤其是这类"修法"：`--force`、`--legacy-peer-deps`、关掉证书校验、`chmod 777`、关掉杀软或防火墙、降低安全设置、`sudo` 一把梭。它们让报错消失，不等于问题解决；涉及安全设置的要先问用户。
- **一次只换一个变量**，用一手证据确认真的修好了（见 screenshot-first）。
- **留下出处**：在汇报、提交信息或代码注释里附上 issue / 文档链接。下次遇到、或者别人来改时，知道为什么这样写。

## 查不到时

- 换两三轮关键词仍然没有结果，就回到自己分析。这时你已经排除了"这是个已知问题"，花时间自己推是值得的。
- 自己分析时也要**留痕**：做了什么实验、排除了什么。
- 准备说"做不到"或者改用兜底方案时，转到 never-give-up-early：那里要求多路调研和证据。
- 没有联网能力：先看本机的文档、源码和 `--help`；还不够，就把打算搜的关键词和来源列给用户，而不是一直猜下去。

## 别让"查"变成新的死磕

- 查是为了少走弯路，不是代替动手。可以一边跑最小复现，一边查。
- 普通问题：一两次搜索，看前几个靠谱的结果，几分钟内应该有方向。
- 读了十几篇还没头绪，说明关键词或问题定位错了：回去看报错原文是不是读全了（见 look-beyond-the-log），而不是继续读第二十篇。

## 常见误区

| 误区 | 实际 |
| --- | --- |
| "再试一次就好了" | 第三次猜的命中率并不比前两次高；第一页搜索结果常常直接给出原因 |
| "这么简单的东西自己写更快" | 写主路径快，边界情况慢：CSV 引号、时区、编码、重试的幂等性 |
| "我记得这个 API 是这么用的" | 记忆可能对应旧版本；看一眼当前文档只要几十秒 |
| "搜到的答案能用就行" | 不对版本、不懂原理的修法，常常只是把报错藏起来 |
| "用户让我修，就该自己推出来" | 用户要的是修好，不是看你从头推导一遍 |
| "我把问题描述清楚再搜" | 用报错原文搜，比用你概括的描述搜准得多 |

## 检查清单

- [ ] 这个报错是不是来自我没写的代码？是的话，在第二次修改之前用原文搜过了吗？
- [ ] 同一问题是不是已经失败了两次？是的话，停下来查
- [ ] 我现在的修改有依据吗，还是在"试试看"？
- [ ] 要手写的东西，标准库、现有依赖或成熟的包里有没有？
- [ ] API 用法是查过当前版本文档，还是凭记忆？
- [ ] 搜到的方案对得上我的版本和平台吗？我知道它为什么有效吗？
- [ ] 有没有照抄 `--force`、关校验、降安全设置这类修法？
- [ ] 出处链接记下来了吗？
