# 不要过早放弃，也不要过早降级

两种表现，同一个病根：**证据还不够，就收敛到了一个更小的目标。**

- **放弃**：试了几种方法都失败，就说"走不通 / 技术上不可行 / 不值得继续"。
- **降级**：主方案（硬件加速、GPU/3D 渲染、原生实现、官方接口、完整功能）出现一次异常，就退到兜底方案（软件渲染、CPU 模式、兼容模式、降级实现、mock、关掉功能）。

兜底方案之所以诱人，是因为它"肯定能跑"。但它肯定能跑，是因为它放弃了你本来要的东西。**退到兜底不是解决问题，是换了一个更小的问题。**

## 反面案例一：只试了一轮就判了"死刑"（真实发生）

**目标**：让一个商用软件在虚拟机里正常启动。它启动时会检测运行环境，检测到虚拟机就拒绝运行。

**AI 的做法**：自己逐项改了 CPU 标识、固件信息、网卡、显卡加速、十几条虚拟机配置项和注册表。全部失败后得出结论："这条路走到头了，它的检测层次足够深，不值得继续。"

**用户的反问**："你只凭一篇二手转载帖、自己试了一轮，就判了死刑。调研太少。"

**之后**：开了 4 路互相独立的调研，其中一路直接找到了一个现成的开源驱动，装上就解决了。**前后 30 分钟。**

## 反面案例二：把更新时的重启当成"主方案不可行"（真实发生）

**目标**：给虚拟机调大显存，走 3D 加速渲染。

**发生了什么**：改完显存配置后重启虚拟机。Windows 这时正好在装更新，重启过程中**关机了好几次**，这是 Windows Update 的正常流程。

**AI 的做法**：把中途的一次关机当成了"重启完成了 / 重启失败了"，没有确认虚拟机当前的状态，就断定改显存的方法不可行。用户明确说了"现在正在更新"，它依然坚持这个结论，自己决定回退到软件渲染。

**结果**：主方案其实没有问题，只是还没等它跑完。软件渲染性能更差，后面还得绕回来，白白浪费了大量时间。

## 问题出在哪

| 实际行为 | 应有的行为 |
| --- | --- |
| 看到一个现象（关机、黑屏、超时）就当成结论（失败） | 先问：这是终态，还是过渡状态？ |
| 自己穷举 5~6 种配置 | 先搜"别人是怎么解决这个问题的" |
| 读完一篇文章就下结论 | 覆盖代码托管、官方文档、论坛，中英文都查 |
| 把"我试的都不行"当成"没有可行方案" | "我试的"只是全部方案里很小的一块 |
| 用"层次太深""太复杂"这种模糊判断收尾 | 要么给出具体的排除证据，要么继续找 |
| 用户说了当前状态，仍然坚持自己的推断 | 用户对自己机器的了解是一手信息，优先采信 |
| 自己决定降级 | 降级会降低目标，要用户同意 |

## 触发信号：发现自己正要说这些话时

- "这条路走不通 / 走到头了 / 不值得继续"
- "技术上不可行 / 应该不支持 / 没办法绕过"
- "建议换个方案"（但其实没有确认原方案已经被排除）
- "这个方法好像不行，我们改用……（软件渲染 / CPU / 兼容模式 / 旧版本 / mock）"
- "为了稳妥起见，先关掉……（硬件加速 / 这个功能 / 这个优化）"
- "可能是 X 导致的，建议你手动……"（把问题推回给用户）
- 看到**重启、关机、黑屏、闪退、卡住、超时、第一次很慢**，就准备下"失败"的结论

## 第一步：先确认真的失败了

很多看起来像失败的现象，其实只是还没结束：

| 现象 | 常见的正常原因 |
| --- | --- |
| 重启时关机好几次、反复重启 | Windows Update 安装更新，一次更新可能重启多次 |
| 改完硬件配置后第一次启动很慢、黑屏一会儿 | 系统在识别新硬件、装驱动、重建缓存 |
| 显卡/驱动相关改动后分辨率变低、画面闪 | 驱动正在安装或切换，装完通常要再重启一次 |
| 第一次运行特别慢 | 着色器编译、JIT、缓存预热、依赖下载 |
| 服务启动后一段时间连不上 | 还在初始化、迁移数据库、等健康检查 |
| 构建/安装好久没输出 | 在下载、在编译、或者在等输入（见 dialog-handling） |

不要从一个瞬间的现象推断，去看它**现在**到底在干什么（见 screenshot-first）：

- **看画面**：截目标窗口（见 background-friendly）。"正在处理更新 35%"和蓝屏、和登录界面，是完全不同的结论。
- **查状态**：

  ```powershell
  Get-VM -Name "MyVM" | Select-Object Name, State, Uptime              # Hyper-V
  ```
  ```bash
  vmrun list                                                            # VMware
  VBoxManage showvminfo "MyVM" --machinereadable | grep -i VMState      # VirtualBox
  ```

- **查日志**：

  ```powershell
  # 1074 = 某个进程发起了关机/重启（会写明是谁、为什么，比如 TrustedInstaller / 更新）
  # 6008 = 意外关机，这才是异常
  Get-WinEvent -FilterHashtable @{LogName='System'; Id=1074,6008; StartTime=(Get-Date).AddHours(-2)} |
    Select-Object TimeCreated, Id, Message
  ```

- **等它到终态再判断**：用条件等待，等"登录界面出现 / 服务响应 / 状态变为 Running 且稳定"，并设总超时（见 no-blind-wait）。

**用户说的状态，优先采信。** 用户告诉你"它正在更新"、"那是正常的"、"再等一下"，比你从一个现象推出来的结论可靠得多：

```
✗ "我理解，但从目前的情况看，改显存的方案可能不可行，我先切换到软件渲染。"
✓ "好的，那我等更新完成、进入系统后再验证 3D 加速是否生效。"
```

仍有疑虑时，**说出来、给出证据，让用户决定**，而不是在用户反对的情况下自己改路线。

主方案"失败"要有这些证据：到了终态问题依然存在；有具体的错误码、日志、驱动报错（如 `dxdiag` 显示加速不可用）；再试一次可复现。

## 第二步：多路调研，至少 3 路，每路角度不同

确认真的失败了，也不等于没有办法：

```
角度 A：针对这个具体机制，有没有专用工具、补丁、绕过方案
角度 B：换环境、换前提，能不能根本不触发它
角度 C：绕开这个环节，从别的入口达成目标
角度 D：重审自己的分析前提，哪个假设没有验证就被当成了事实
```

- 有子智能体或并行能力时，**一次全部派出去**。每一路都只给原始事实，**不要把你的既有结论喂给它们**，并明确允许它们推翻你。
- 没有并行能力时，按这几个角度依次搜索，每个角度用不同的关键词。
- 没有联网能力时，把你会去搜的关键词和来源列给用户，请用户帮忙查，或者授权你用别的方式查。

## 第三步：检索既有方案

```
代码托管：搜 "<机制或报错原文> fix | workaround | patch | tool"
官方来源：文档 / changelog / issue tracker（含已关闭的 issue）/ 源码本身
社区：这个领域老手聚集的论坛和邮件列表，中英文各查一遍
长文：论文、会议演讲、技术博客的原始出处（不要只看转载）
```

**用报错原文搜索**，不要只用你自己概括的描述来搜。找"已经解决过这个问题的人"，比重新发明一遍快一个数量级。

## 第四步：审计假设

- 判定"失败"的标准对吗？（比如把"没弹窗"当成"程序要退出"，把"更新中的关机"当成"重启失败"）
- 失败信息读完整了吗？日志、报错的后半截、退出码、弹窗原文（见 dialog-handling、screenshot-first）
- 有没有一条明显的路径完全没考虑？（换方案、换平台、换入口、换版本）
- 问题会不会根本不在你以为的位置？（以为在 A 层，实际在 B 层）
- 每次改动是一次只改一个变量吗？同时改五处、全部失败，什么也排除不了。

## 什么情况才真的可以停

只有三种：

1. **可行路径已经穷举**，每条都有具体的失败原因（不是"感觉很难"）。
2. **收益和代价严重不匹配**，而且判断基于真实成本，不是猜测（比如需要专用硬件、要停机、会破坏数据）。
3. **目标本身有问题**（目标已经不存在，或者达成了也没用）。

**"我试了几次都失败"不属于其中任何一种。**

真要说"不行"时，用这个格式：

```
目标：……
已排除的路径：
  1. <路径> —— 失败证据：<具体报错 / 数据 / 文档出处>
  2. ……
查过的来源：<代码托管搜索词、issue 链接、文档章节……>
还没试的路径及其代价：……
如果要继续，需要：<权限 / 硬件 / 时间 / 用户的决定>
```

写不出"失败证据"和"查过的来源"这两栏，就说明还没到可以说"不行"的时候。

## 真的要降级时

1. **先问用户**，说清楚代价：

   ```
   ✓ "3D 加速在更新完成、重启两次后依然不可用，dxdiag 显示 '不可用'，驱动报错 xxx。
      可以先切到软件渲染让流程继续，但性能会差很多。要切，还是我继续查驱动的问题？"
   ```

2. 用户同意了，也要**标明这是临时的**，记下回到主方案还缺什么。
3. 不要在兜底方案上越走越远，把它当成了新的主线。

## 边界

- **调研有成本**。长时间调研时，每一轮都简短告诉用户：试了什么、排除了什么、下一步打算做什么，让用户可以随时叫停或调整方向。
- **权限拒绝、安全限制、用户明确的约束不算技术障碍**。不要把"想办法绕过它们"当成坚持。遇到这些情况，说明情况，问用户。
- 用户本来就说"先用最简单的能跑就行"，用兜底是对的。
- 时间紧急、需要先恢复服务时，可以临时兜底，但要告诉用户，并且回头继续修主方案。
