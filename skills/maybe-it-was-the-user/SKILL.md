# 先想想：会不会是用户干的

用户在你工作时**还在正常用这台电脑**（见 background-friendly）。所以你看到的每一个"意外"，都有两种来源：

```
A. 程序自己出了问题：崩溃、异常退出、被系统杀掉
B. 用户做了操作：关掉了窗口、误触了关闭按钮、按了 Alt+F4 / Ctrl+C、手动改了文件、切了分支
```

AI 的默认反应几乎总是 A，于是开始读日志、加打印、改代码、重启、再重启，排了二十分钟错，其实用户只是顺手把那个挡路的窗口关了。更糟的情况：用户手动改了文件，你以为是"自己的改动丢了"，把它覆盖回去。

## 典型案例

**场景**：AI 启动了一个 GUI 程序在后台测试。几分钟后发现进程不在了。

**AI 的做法**：断定"程序启动后崩溃"，开始翻代码找崩溃原因，加日志、改初始化逻辑、重新编译、再启动……

**实际情况**：窗口弹出来挡住了用户正在做的事，用户顺手点了关闭。进程退出码是 0，程序日志最后一行就是正常的退出流程。**一眼就能看出来的东西，没看。**

## 触发信号

出现下面这些情况时，先停一下，别直接进排错流程：

| 你看到的 | 可能的用户操作 |
| --- | --- |
| 你启动的程序/窗口/浏览器标签不见了 | 用户关掉了它（嫌挡路、误触、以为是自己开的多余窗口） |
| 终端里的命令被中断，`^C`、退出码 130 / `-1073741510`（0xC000013A） | 用户在那个终端按了 Ctrl+C，或关掉了终端窗口 |
| 你改过的文件内容变了 | 用户手动编辑了、编辑器格式化了、用户撤销了你的改动 |
| git 分支、暂存区、提交变了 | 用户自己 checkout / commit / stash 了 |
| 窗口位置、大小、焦点变了；截图里多了别的窗口 | 用户在用电脑 |
| 设置、配置项被改回去 | 用户不想要这个改动 |
| dev server、端口、容器没了 | 用户停了它，或者重启了电脑/IDE |

关键特征：**变化来得突然、没有任何报错、发生在你没操作的时候。**

## 先取证，再下结论

区分"崩溃"和"被正常关闭"，大多数时候几秒钟就能做到：

### 1. 退出码

```powershell
# 用 -PassThru 启动的进程，之后可以查退出码
$p = Start-Process app.exe -PassThru
# ...之后
$p.HasExited; $p.ExitCode
```

| 退出码 | 含义 |
| --- | --- |
| `0` | 正常退出，最常见的是用户关闭了窗口 |
| `130`（Unix）/ `-1073741510` = `0xC000013A`（Windows） | Ctrl+C 或关闭了控制台窗口 |
| `143` / `137`（Unix） | 收到 SIGTERM / SIGKILL，可能是用户 `kill`，也可能是 OOM |
| `-1073741819` = `0xC0000005` | 访问违例，**这才是崩溃** |
| `-1073740791` = `0xC0000409` | 栈溢出 / 安全检查失败，崩溃 |
| `0xE0434352` | .NET 未处理异常，崩溃 |

### 2. 系统事件日志（Windows）

真正的崩溃几乎一定会在 Application 日志里留下记录：

```powershell
Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000,1001,1026; StartTime=(Get-Date).AddMinutes(-30)} -ErrorAction SilentlyContinue |
  Where-Object { $_.Message -match 'app\.exe' } | Select-Object TimeCreated, Id, Message
```

`1000` = Application Error，`1001` = Windows Error Reporting，`1026` = .NET Runtime。**什么都没有，就是一个强烈的"正常关闭"信号。**

### 3. 程序自己的日志

看最后几行：是正常的 shutdown 流程（"closing"、"saving settings"、`WM_CLOSE`、`beforeunload`、`app.on('window-all-closed')`），还是戛然而止、或者一个异常堆栈？

### 4. 时间线

- 消失的时间点，你在做什么？如果你那时没碰它，而它只是"突然没了"，人为操作的可能性很高。
- 程序之前已经稳定运行了一段时间，没有新代码、新输入，不太可能突然自己崩。
- 文件被改：看修改时间和内容。改动不是你写的样子（不同的风格、只改了一处、撤销了你的某段改动），就是用户或用户的编辑器干的。

```bash
git diff            # 看到底变了什么
git reflog -n 10    # 分支/提交变化是谁、什么时候做的
```

## 判定之后怎么做

### 证据指向用户操作

**不要排错，不要改代码。** 简短地问一句，把你看到的证据带上，让用户一秒就能回答：

```
✓ "测试程序被关掉了（退出码 0，日志是正常退出流程，没有崩溃记录）。是你关的吗？
   需要的话我换成最小化启动，不会再挡到你。"
✓ "config.json 里我加的那一项被删了，是你改的吗？如果你不想要这个改动，我就不加了。"
```

同时反思：**用户为什么要关它？** 最常见的原因是你的窗口打扰到了用户：弹到了前台、挡住了正在用的东西。下次用 background-friendly 的方式最小化、不激活地启动。

### 证据指向崩溃

正常进入排错流程，并把证据（退出码、事件日志、堆栈）作为排错的起点。

### 证据不够

两种可能都说出来，问用户，而不是默认按 A 处理：

```
✓ "程序退出了，退出码 1，日志里没有异常也没有正常退出记录。是你关掉的吗？
   如果不是，我再去查是不是启动阶段出了问题。"
```

## 不要做的事

- **不要反复自动重启用户关掉的东西。** 用户关一次，你开一次，用户再关……这是在跟用户抢电脑。关过一次，就问。
- **不要把用户的改动"修复"回去。** 文件内容和你记忆中的不一致时，先重新读取文件，在当前内容的基础上继续改，不要用你缓存的旧版本覆盖。被撤销的改动不要悄悄再加回去。
- **不要撤销用户的 git 操作。** 分支被切走了，别自作主张 checkout 回去、更不要 reset / stash 掉用户的东西。先问。
- **不要因此就怪用户。** 问的语气是确认事实，不是追责："是你关的吗？" 而不是 "请不要关闭程序"。

## 边界

- 你在一个隔离环境（CI、容器、远程机器、用户明确说过不会碰的虚拟机）里工作时，用户操作的可能性很低，正常排错即可。
- 有明确的崩溃证据（崩溃退出码、事件日志、异常堆栈、dump 文件）时，不必问，直接排错。
- 同一个现象**在用户没碰的情况下稳定复现**，就不是用户操作了。
- 后台、最小化运行、本来就没打扰用户的进程，第一次意外退出时可以先看证据再决定；证据指向正常关闭时依然要问，而不是悄悄重启。

## 检查清单

- [ ] 我准备排错的这件事，有没有可能是用户做的？
- [ ] 看过退出码了吗？是 0 / Ctrl+C，还是崩溃码？
- [ ] 系统事件日志、程序日志里有崩溃记录吗？
- [ ] 变化发生时我在操作它吗？之前它稳定运行了多久？
- [ ] 文件/git 状态变了：我是在当前内容上继续，而不是用旧版本覆盖？
- [ ] 像是用户操作时：问了一句并附上证据，而不是排错或反复重启？
- [ ] 想过用户为什么会关它吗？下次能不能不打扰？
