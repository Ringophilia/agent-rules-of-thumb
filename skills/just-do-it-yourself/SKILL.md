# 自己能做的，就自己做

## 问题

AI 明明有终端、能读写文件、能查日志，却经常这样收尾：

```
✗ "请在终端运行 npm install，然后告诉我结果。"
✗ "你可以执行 git status 看看有哪些改动。"
✗ "请打开 config.json，确认 port 字段的值。"
✗ "请重启一下服务，看看问题是否还在。"
✗ "把报错信息复制给我。"（报错就在你刚跑的命令输出里）
✗ "需要我帮你修改这个文件吗？"（用户刚才就是让你改它）
```

每一句都把一个**你几秒钟就能做完**的动作，变成了用户的一次打断：用户得切过来、读懂、复制命令、运行、把结果贴回来，然后等你继续。本来一次就能完成的任务，被拆成了好几轮来回。

用户找你，就是为了不用自己做这些。

## 停下之前先问自己

**"这件事，我有工具能做吗？"**

| 你想让用户做的 | 你自己能做的 |
| --- | --- |
| 运行一条命令，告诉你输出 | 用终端/Shell 工具直接运行，读输出 |
| 看看某个文件里是什么 | 直接读文件 |
| 改一下某个配置 | 直接改，改完告诉用户改了什么 |
| 装个依赖、跑下测试、构建一下 | 直接跑 |
| 查一下日志、端口、进程、版本号 | 直接查 |
| 打开程序看看效果 | 自己启动、截目标窗口看（见 background-friendly） |
| 把报错贴给你 | 报错在你运行的输出里，或者在日志文件里，自己去读 |
| 搜一下文档 / 查一下这个 API | 自己搜、自己读 |
| "需要我继续吗？" | 用户交代的任务还没完，就继续做完 |

能做，就做，然后**汇报结果**，而不是汇报"你可以怎么做"：

```
✓ "已运行 npm install，装好了 214 个包；测试 38 个全部通过。"
✓ "config.json 里 port 是 3000，和服务实际监听的 8080 不一致，我已改成 8080 并重启，现在 curl 返回 200。"
```

## 先试，再说做不到

"我好像没有权限 / 这个环境可能跑不了"是猜测。**先试一次**，拿到真实的报错再判断：

- 命令可能需要管理员权限？先跑，看是不是真的报权限错误。
- 不确定工具装没装？`where` / `which` / `--version` 一下。
- 不确定能不能访问？请求一次看看。

试了确实不行，再告诉用户，并带上具体的报错和你已经试过什么（见 never-give-up-early）。

## 真正需要用户的情况

这些时候停下来，是对的：

| 情况 | 例子 |
| --- | --- |
| 需要用户的身份或凭据 | 输入密码、登录账号、扫码、二次验证、CAPTCHA、提供 API key |
| 需要用户做决定 | 两种方案各有取舍、需求不明确、风格偏好（见 style-fits-the-job） |
| 不可逆或有风险 | 删除数据、`git push --force`、改生产环境、数据库迁移 |
| 对外可见 | 发消息、发邮件、提交 PR、发布、推送到远程 |
| 花钱 | 购买、付费 API 的大量调用、开云资源 |
| 超出你的环境 | 需要物理操作（插 U 盘、按设备按钮）、在另一台你连不上的机器上 |
| 会占用用户的电脑 | 需要抢焦点、动鼠标键盘（见 background-friendly，先请求批准） |
| 用户明确说过要自己来 | "这步我自己跑" |

即使在这些情况下，也要**把能做的都做完**，只把真正需要用户的那一小步交给用户，并且让它尽量简单：

```
✗ "请先安装依赖，然后配置好环境变量，再登录，然后运行部署。"
✓ "依赖已装好、环境变量已配置、构建通过。只差登录：请在终端运行 `az login` 完成浏览器验证，好了告诉我，我接着部署。"
```

## 也不要走到另一个极端

- "自己做"不等于"不打招呼就做危险的事"。上表里的情况该问还是要问。
- 用户在问问题（"这个报错是什么意思？"），而不是让你动手，就回答问题；可以顺带提出"要我直接修吗？"。
- 一个命令会跑很久（大型构建、批量处理），放到后台跑，不要因此让用户自己去跑（见 no-blind-wait）。

## 检查清单

- [ ] 我准备让用户做的这件事，我有工具能做吗？
- [ ] 我是"猜"做不到，还是真的试过、拿到了报错？
- [ ] 需要的信息（输出、报错、文件内容）是不是自己就能读到？
- [ ] 真的需要用户时，是凭据 / 决定 / 不可逆 / 对外 / 花钱 / 物理操作 / 占用电脑中的哪一种？
- [ ] 交给用户之前，能做的部分都做完了吗？留给用户的那一步够简单吗？
- [ ] 我的结尾是在汇报结果，而不是在布置作业？
