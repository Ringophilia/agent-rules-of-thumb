# 不要太早退到兜底方案

## 反面案例（真实发生）

**目标**：给虚拟机调大显存，走 3D 加速渲染。

**发生了什么**：改完显存配置后重启虚拟机。Windows 这时正好在装更新，重启过程中**关机了好几次**，这是 Windows Update 的正常流程。

**AI 的做法**：

1. 把中途的一次关机当成了"重启完成了 / 重启失败了"，没有去确认虚拟机当前到底是什么状态。
2. 由此断定"改显存的方法不可行"。
3. 用户明确告诉它"现在正在更新"，它依然坚持这个结论。
4. 自己决定回退到软件渲染，放弃了原来的 3D 渲染路线。

**结果**：主方案其实没有问题，只是还没等它跑完。退到软件渲染之后性能更差，后面还得再绕回来，白白浪费了大量时间。

## 问题出在哪

| 实际行为 | 应有的行为 |
| --- | --- |
| 看到一个现象（关机）就当成结论（失败） | 先问：这是终态，还是过渡状态？ |
| 没有确认虚拟机实际在干什么 | 看控制台画面、查状态、查日志 |
| 用户说了"正在更新"，仍然坚持自己的推断 | 用户对自己机器的了解是一手信息，优先采信 |
| 一次异常就判定主方案不可行 | 主方案失败要有证据：具体的错误、可复现 |
| 自己决定降级 | 降级会降低目标，要用户同意 |

兜底方案之所以诱人，是因为它"肯定能跑"。但它肯定能跑，是因为它放弃了你本来要的东西。**退到兜底不是解决问题，是换了一个更小的问题。**

## 触发信号

你发现自己准备说这些话的时候，停一下：

- "这个方法好像不行，我们改用 ……（软件渲染 / CPU / 兼容模式 / 旧版本 / mock）"
- "为了稳妥起见，先关掉 ……（硬件加速 / 这个功能 / 这个优化）"
- "看起来不支持，我换一种简单的实现"
- 看到**重启、关机、黑屏、闪退、卡住、超时、第一次很慢**，就准备下"失败"的结论

## 先判断：是过渡状态，还是真的失败？

很多看起来像失败的现象，其实只是还没结束：

| 现象 | 常见的正常原因 |
| --- | --- |
| 重启时关机好几次、反复重启 | Windows Update 安装更新（"正在处理更新，请勿关闭计算机"），一次更新可能重启多次 |
| 改完硬件配置后第一次启动很慢、黑屏一会儿 | 系统在识别新硬件、装驱动、重建缓存 |
| 显卡/驱动相关改动后分辨率变低、画面闪 | 驱动正在安装或切换，装完通常要再重启一次 |
| 第一次运行特别慢 | 着色器编译、JIT、缓存预热、依赖下载 |
| 服务启动后一段时间连不上 | 还在初始化、迁移数据库、等健康检查 |
| 构建/安装好久没输出 | 在下载、在编译、或者在等输入（见 dialog-handling） |

## 用一手证据确认状态

不要从一个瞬间的现象推断，去看它**现在**到底在干什么（见 screenshot-first）：

- **看画面**：截虚拟机控制台窗口（见 background-friendly）。"正在处理更新 35%"和蓝屏、和登录界面，是完全不同的结论。
- **查宿主机上的虚拟机状态**：

  ```powershell
  Get-VM -Name "MyVM" | Select-Object Name, State, Uptime              # Hyper-V
  ```
  ```bash
  vmrun list                                                            # VMware
  VBoxManage showvminfo "MyVM" --machinereadable | grep -i VMState      # VirtualBox
  ```

- **查客户机里的日志**（能进系统后）：

  ```powershell
  # 1074 = 某个进程发起了关机/重启（会写明是谁、为什么，比如 TrustedInstaller / 更新）
  # 6008 = 意外关机，这才是异常
  Get-WinEvent -FilterHashtable @{LogName='System'; Id=1074,6008; StartTime=(Get-Date).AddHours(-2)} |
    Select-Object TimeCreated, Id, Message
  ```

- **等它到终态再判断**：用条件等待，等"登录界面出现 / 服务响应 / 状态变为 Running 且稳定"，并设总超时（见 no-blind-wait），而不是看到第一次关机就下结论。

## 用户说的状态，优先采信

用户告诉你"它正在更新"、"那是正常的"、"再等一下"，这是**用户对自己机器的一手信息**，比你从一个现象推出来的结论可靠得多。

```
✗ "我理解，但从目前的情况看，改显存的方案可能不可行，我先切换到软件渲染。"
✓ "好的，那我等更新完成、进入系统后再验证 3D 加速是否生效。"
```

如果你仍然有疑虑，**说出来、给出证据，然后让用户决定**，而不是在用户反对的情况下自己改路线。

## 确认主方案失败，要有证据

只有拿到这些证据，才能说主方案"不行"：

- 到了终态（系统已经完整启动、程序已经完全加载），问题依然存在
- 有具体的错误：错误码、日志、驱动报错、`dxdiag` / `glxinfo` 显示加速不可用
- 可复现：再试一次，同样的问题
- 排查过常见原因（驱动没装、配置没生效、版本不匹配），见 never-give-up-early

## 真的要用兜底时

1. **先问用户**，说清楚代价：

   ```
   ✓ "3D 加速在更新完成、重启两次后依然不可用，dxdiag 显示 '不可用'，驱动报错 xxx。
      可以先切到软件渲染让流程继续，但性能会差很多。要切，还是我继续查驱动的问题？"
   ```

2. 用户同意了，也要**标明这是临时的**，记下回到主方案还缺什么。
3. 不要在兜底方案上越走越远，把它当成了新的主线。

## 边界

- 用户本来就说"先用最简单的能跑就行"，用兜底是对的。
- 主方案的失败已有明确、可复现的证据，并且用户同意改方向，就改。
- 时间紧急、需要先恢复服务时，可以临时兜底，但要告诉用户，并且回头继续修主方案。
