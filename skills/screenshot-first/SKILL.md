# 一手证据优先

叫 screenshot-first，是因为截图是最典型的一手证据。原则本身适用于任何可观测系统：GUI、网页、服务、容器、构建流水线、批处理。

**一手证据 = 最终使用者实际拿到的东西。** 用户看的是画面，一手证据就是截图；调用方拿到的是响应体，一手证据就是 `curl -i` 的完整输出；交付的是安装包，一手证据就是把它装上跑一次。

## 证据等级

```
1. 一手效果：截图 / 渲染帧 / 真实响应体 / 实际运行产物   ← 使用者看到什么就是什么
2. 结构枚举：窗口树 / DOM / 无障碍树 / 端口表 / 容器列表  ← 能发现被遮挡、被隐藏的实体
3. 按唯一 ID 查询：pid / 请求 id / 事务 id              ← 精确，但得先拿到 ID
4. 按名字查询：进程名 / 容器名 / 服务名                 ← 最弱：名字可以被改，也会重名
```

高等级和低等级冲突时，先信高等级，**然后去搞清楚低等级为什么会说错**。冲突本身就是线索。

## 宣布"完成"之前

对用户说"已修好 / 已启动 / 已部署 / 测试通过"之前，必须拿到最终效果的一手证据。拿不到时，就明确说"**未验证**"，并说明缺了哪一步，不要用间接指标冒充。

```
✗ "构建成功了，问题应该解决了。"
✓ "构建成功；重新运行后截图显示错误弹窗不再出现，主界面正常加载。"
✓ "构建成功，但我没法在这个环境里运行 GUI，修复效果还未验证。"
```

## 间接指标为什么会骗人

实测案例：程序运行后，按名字查进程返回空，`MainWindowTitle` 也是空的，据此判断"已退出"。但截图显示窗口就在屏幕中央，等着人去点。原因是运行时把映像名改成了一串数字。

同类失效在任何平台都有：

| 现象 | 真实原因 |
| --- | --- |
| 按名字查不到进程或容器 | 名字被运行时改写，或者查询维度不同 |
| 进程在，但窗口标题为空 | 窗口属于另一个 session 或桌面 |
| 枚举不到明明存在的窗口 | 脚本跑在非交互 session（比如服务、计划任务的 session 0） |
| 截图全白或全黑 | 同上，没有可以捕获的桌面；或者窗口开了防截屏 |
| 构建退出码 0，产物却不可用 | 退出码只说明"没抛异常" |
| 接口返回 200，页面没更新 | 缓存层、CDN、前端状态机 |
| 容器在跑，服务不通 | 端口映射、网络命名空间、就绪延迟 |
| 测试全部通过，功能还是坏的 | 测试没覆盖到这条路径，或者 mock 掉了真正出问题的那一层 |

## 正确做法

**先想清楚要回答什么问题，再取证据。** "截一张看看"不如"截一张，确认登录框是否已经消失"。

**动作前后各取一次**，对比着看：动作前那张是基线，动作后那张才能说明这个动作造成了什么变化。

取证据的方式举例：

```powershell
vmrun -T ws -gu USER -gp PASS captureScreen VMX out.png    # 虚拟机画面
curl.exe -i http://host/api/x                               # 带响应头的真实响应
```

桌面程序截图时只截目标窗口，不截全屏（用户可能正在用电脑）：用 background-friendly 的 `capture-window.ps1`，被遮挡或最小化的窗口也能截，而且不抢焦点。

浏览器里：截图看布局；看文字时，读页面文本或无障碍树往往更准、更省 token，它们同样是一手证据。

**需要唯一 ID 时，从持有资源的实体反查**，不要按名字猜：

```
窗口     → GetWindowThreadProcessId → pid
监听端口 → netstat -ano / ss -ltnp  → pid
容器     → docker inspect           → 镜像与入口进程
```

这样拿到的 ID，一定属于真正持有这个资源的实体。

**判断实体是否存在，用结构特征**（类名、尺寸、端口、挂载、响应头），不要用文本匹配。文本会因为编码、语言、动态内容而失效。

## 一手证据也有盲区

| 盲区 | 表现 | 补救 |
| --- | --- | --- |
| 遮挡 | 截图里只有主窗口，被压在下面的模态框拍不到 | 补一次全量结构枚举（见 dialog-handling） |
| 冻结画面 | 程序已经挂了，窗口还显示着最后一帧 | 查 "未响应" / `IsHungAppWindow`，做一次交互后再截 |
| 时机 | 动作后马上截，界面还没刷新 | 等条件成立再截（见 no-blind-wait） |
| 观测错对象 | 截的是另一台显示器、另一个虚拟机、另一个标签页；访问的是 staging 而不是 prod；看到的是缓存 | 确认观测点和执行点是同一个环境 |
| 偶然性 | 成功了一次，不等于稳定成功 | 关键结论多验证一次，或者换一条输入路径再验证 |

所以一手证据和结构枚举要互补：

```
一手效果   → 使用者视角，最终呈现
结构枚举   → 系统视角，全量实体
两者结合   → 完整状态
```

典型场景：截图里只有一个主窗口，但窗口枚举发现同一个进程还有一个 `#32770`，`Visible=True`，位置在主窗口下面。正是这个对话框在阻塞主窗口的消息循环，所以才"点了没反应"。

## 检查清单

- [ ] 取证据之前，先想清楚这次要回答的问题
- [ ] 动手前取一次基线，动手后再取一次
- [ ] 间接指标查不到时，不要直接下"不存在 / 已退出"的结论
- [ ] 要 ID 就从资源反查，不要按名字猜
- [ ] 一手证据看不出问题时，补一次全量结构枚举（含隐藏、被遮挡的）
- [ ] 确认观测点和执行点是同一个环境
- [ ] 宣布完成之前，有最终效果的一手证据吗？没有就写"未验证"
